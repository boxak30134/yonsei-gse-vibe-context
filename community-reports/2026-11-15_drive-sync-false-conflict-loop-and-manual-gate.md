# 클라우드 드라이브 양방향 동기화 시 충돌 사본 무한 복제 및 자동 업로드 방지 패턴

## 1. 문제 현상
- 문서 편집·필기 중 로컬 자동 저장(`save()`)과 백그라운드 동기화가 맞물릴 때, 원격 파일을 수정한 적이 없는데도 매 동기화 주기마다 `(충돌 사본 YYYY-MM-DD...)` 파일이 계속 복제되어 생성됨.
- 사용자가 명시적으로 업로드하지 않은 로컬 전용 문서까지 동기화 시점에 자동으로 클라우드에 업로드되거나, 네트워크 재연결 시 예기치 않은 동기화가 실행됨.

## 2. 근본 원인
1. **업로드 전 클라이언트 시각으로 `lastSyncedAt` 기록 + 보조 사이드카 타임스탬프 미추적**:
   - 동기화 루프 시작 시점에 `const now = Date.now()`를 미리 잡아두고, 본문(`.md`)과 메타데이터 사이드카(`.json`)를 순차 업로드한 뒤 `lastSyncedAt: now`를 저장하면, 클라우드 서버가 부여하는 `modifiedTime`(특히 두 번째로 올라가는 사이드카 파일의 `modifiedTime`)이 클라이언트 시계 오차나 네트워크 지연으로 인해 `now`보다 수백 ms ~ 수 초 뒤가 된다.
   - 다음 동기화 시 `sidecarModifiedMs > lastSyncedAt` 조건이 매번 `true`가 되어 **내가 방금 올린 파일을 원격 변경분으로 오판**하고, 편집 중인 `localDirty` 상태와 겹쳐 양방향 충돌 분기가 무한 반복된다.
2. **자동 저장 디바운스 + 온라인 리스너 + 동시 실행 락 부재**:
   - 필기/타이핑 중 자동 저장마다 백그라운드 동기화가 트리거되면 동시 요청 경합과 편집 중 충돌이 폭증한다.
3. **미연결 로컬 문서의 자동 업로드**:
   - 원격 파일 ID(`remoteFileId`)가 없는 로컬 전용 문서를 전체 동기화 루프에서 일괄 업로드하면, 사용자가 의도하지 않은 초안·개인 메모가 클라우드에 무단 업로드된다.

## 3. 해결 패턴
1. **서버 타임스탬프 정확 추적 및 업로드 후 `lastSyncedAt` 확정**:
   - 본문과 사이드카의 서버 `modifiedTime`을 각각 별도 필드(`remoteModifiedTime`, `remoteSidecarModifiedTime`)로 저장해 문자열 동등 비교(`remote.modifiedTime !== local.remoteModifiedTime`)를 우선한다.
   - `lastSyncedAt`은 반드시 업로드 응답을 받은 **이후**에 `Math.max(Date.now(), remoteMdMs, remoteSidecarMs)`로 계산해 저장한다.
2. **수동 트리거 전용 정책 & In-Flight 락**:
   - 자동 저장이나 `online` 이벤트에서 전체 양방향 동기화를 자동 호출하지 않고, 사용자가 `[지금 동기화]` 또는 명시적 `[클라우드에 업로드]` 버튼을 눌렀을 때만 실행한다.
   - 동기화 함수 진입부에 `inFlightPromise` 단일 실행 락을 두어 연속 클릭 시 경합을 방지하고, 업로드 완료 후 열려 있는 편집 세션 메모리(`record`)의 동기화 메타데이터도 DB와 즉시 일치시킨다.
3. **로컬 전용 문서 보존 및 연결 분리**:
   - `remoteFileId`가 없는 로컬 전용 문서는 일반 동기화 루프에서 자동 업로드하거나 원격 부재를 이유로 삭제하지 않으며, 사용자가 명시적으로 업로드를 실행해 `remoteFileId`가 부여된 문서만 이후 증분 동기화 대상에 포함한다.

## 4. 주의점
- 편집 중인 활성 세션이 열려 있을 때 동기화가 DB만 갱신하고 메모리상 세션 레코드를 갱신하지 않으면, 직후 `save()` 시 이전 `remoteModifiedTime`이나 `syncDirty` 상태로 덮어써질 수 있으므로 DB와 활성 세션 레코드를 함께 갱신해야 한다.
